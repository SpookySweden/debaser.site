# Commands

<!-- Moved from .claude/rules/core.md on 2026-11-27 (Luke's context system); facts brought up to date for SERVER. core.md keeps a one-line list. Exact script names live in package.json. -->

- `npm run verify`: lint + tokens + typecheck + build. Must pass before any task counts as done.
- `npm run verify:clean`: the same verify on your latest commit, in a kept clean copy away from other sessions' half-done files (packages installed once, one session at a time; about five minutes, so run it in the background). When verify fails here on files that aren't yours: commit only your own files, run this, push when it passes.
- `npm run tokens`: the theming guard (raw colours, sizes or fonts outside the token files fail it); `-- --write` regenerates the colour block in `app/theme/tokens.css` after a change to `app/lib/ui/themes.ts`. See `docs/theming.md`.
- `npm run styles`: records every element's computed look (`--out <dir>`) and compares two recordings (`--compare <a> <b>`): the proof that a refactor changed nothing visible.
- `npm run dev`: local dev server.
- `npm run checks:changed`: runs only the checks this work can affect, worked out from what each check compiles, reads and walks (a typical change picks about a fifth of them; a shared file picks more; `package.json` and the build settings pick all). This is the one for every task. It prints `FULL RUN DUE` when the whole suite is owed.
- `npm run checks`: the whole suite, `Temp/check-*.cjs` and `scripts/check-*.cjs` (about 125, tracked in git, so every machine has them; several minutes on SERVER, and a heavy step: it takes the one turn). `--only <prefix>` narrows it (`npm run checks:web`). Run it before a big feature (anything built from a SPEC) and when `checks:changed` says it's due: a week since the last, or the last one failed. A failing check is a finding: update it on purpose when the rule really changed and say why, never delete it to go green. New checks stay in `Temp/check-*.cjs` and get committed with the work; anything with a password or address in it stays out (`Temp/check-resend.cjs` is ignored for that reason).
- `npm run capture` then `npm run audit`: the accessibility audit (unnamed controls, tiny tap targets, small text, low contrast). Always capture first, or the audit reads old snapshots.
- `npm run deploy-status`: waits until debaser.site runs the pushed commit (asks `https://debaser.site/api/version`; on the PC it first asks for a rebuild from `main` at once, which then takes a few minutes, so allow up to 15). Exit 0 live, 1 the PC's build failed (see `G:\DEBASER-HOST\logs\update.log`), 2 not pushed, 3 could not ask (the PC off?), 4 still building. `-- --vercel` is the old Vercel check. The only way to wait for a deploy: `gh` is not installed on either machine, and a hand-made polling loop once waited minutes on errors after the build had finished.
- `npm run read`: reads the deployed `/forum` at https://debaser.site and confirms a change is live (`-- --url <address>` for another page, `--absent <text>` to prove something is gone). Use it instead of a hand grep: React wraps text in `<!-- -->` comments, so a plain search for `[ ♪ MUSIC ]` finds nothing even when it's there.
- Screenshots: `playwright-core` drives Chrome if it's there, otherwise Edge. `npm run shot -- --url <address> --out Temp/browse/x.png` takes one; `npm run panes` counts the colours in it; `npm run browser -- --start --signin` opens a reusable session signed in as the kept test account (`TEST ACCOUNT A`; `B` exists for two-person tests; password in the gitignored `.env.test`, which is in `G:\debaser.site` on SERVER: a worktree copies it from there, and any other machine by hand). The tracked tools are all in `scripts/` (see `scripts/README.txt`).
- `npm run db -- "select ..."`: SQL against the live database. Writes need `--write`, and the script prints the statement first; leave that guard alone.
- `npm run web:fetch`: runs the MEDIA page's hourly fetch now instead of at minute 17. It saves into the live stream like the hourly run; my standing OK (2026-11-03) covers running it when you need fresh data to check your work, nothing else.
